KYC Verification Tool for CS agents

CS agents had no way to look up a user's Aadhaar status. Every single query went to the backend team. This is how we fixed that.

Role
Product Designer
Domain
Fantasy Sports Platform
Surface

01 · Background

It was all manual. All of it.

We had already built PAN and bank verification views for CS agents inside the MSD panel. But Aadhaar? Nothing. Product was moving fast, KYC got deprioritised, and before we knew it agents were handling every Aadhaar query by asking users to re-share their details over chat and then raising a backend ticket.

Nobody could see anything. Not the agent. Not the user. If something failed, nobody knew why.

"When a user had a KYC problem, the agent's only option was to ask them for their details again, raise a ticket, and wait. That was it."

02 · Discovery and scoping

First, figure out what you're actually solving

Before jumping into solutions, I wanted to understand the full shape of the problem. What kinds of issues were agents actually dealing with? And which of those could a better tool realistically fix?

1
Mapped the issue types first
There were five things that kept coming up: wrong Aadhaar linked, Aadhaar with a restricted GPS state, no alternate document to fall back on, same Aadhaar used across multiple accounts, and name change requests. Each one needed a slightly different fix. But they all had the same root cause: agents couldn't see anything.
2
Checked what data actually existed on the backend
Turns out a lot was already there. OCR API responses from IDFY, Digilocker responses, image validation results, partner metadata. None of it was surfaced to agents. We also found that verified, pending, and rejected states all existed in the system but only verified was being shown. Small fix, meaningful difference.
3
Cut what didn't need to exist
We had originally considered a standalone KYC verification log page. Then we checked: OCR and Digilocker queries never go into the manual queue. A dedicated log page would always be empty. We dropped it and folded everything into the existing user management page. Less to build, same outcome.
4
Found something nobody had flagged
While mapping the unlinking scenarios, we realised that when an Aadhaar gets verified, the account name silently updates to match it. If someone verified the wrong Aadhaar, the name changed and the original just disappeared. No record. No timestamp. We had to build that from scratch.
03 · Solution

A KYC section inside the MSD panel

We already had a PAN Verification page that agents used. This followed the same pattern. One place to see everything about a user's KYC, and actually do something about it if needed.

Screen 1 — KYC verification queue
The KYC verification queue. Agents can see all pending cases, how closely the PAN name matches the KYC name, and when the document was added. Filterable by Pending, Verified, and Rejected. Alerts can be reassigned across the team.
Screen 2 — KYC document detail view
The document detail view. The Aadhaar image the user actually uploaded sits next to the OCR-extracted fields: name, DoB, state. Below that, the KYC API result, the verification decision, and the raw API response for when agents need to dig deeper.
Full KYC visibility
Doc type, number, name, DoB, GPS state, and verification status surfaced for every user.
Status with rejection reason
Verified, pending, and rejected states shown. Rejected cases surface the reason inline.
OCR and Digilocker detail
Uploaded image, IDFY validation response, OCR API response, and Digilocker response in one panel.
KYC unlink (maker-checker)
Agents can initiate unlink for wrong Aadhaar, restricted state, or multi-account conflicts via a controlled flow.
GST state update
Agents can view and update a user's GST state, a compliance requirement with no prior facility in the panel.
GPS location (read-only)
Current GPS state shown for context. History tracking to be evaluated for compliance.
03b · Something we found along the way

The name change nobody was tracking

When we started mapping the unlinking scenarios, we hit something unexpected. Every time a user verifies an Aadhaar, the account name updates to match the name on that document. Silently. Automatically. No confirmation, no record.

So if someone accidentally verified the wrong Aadhaar, their account name just changed. And once it changed, you had no way to know what it was before. We built the name change trail to fix that.

"Once the name changed, it was just gone. No record of the original, no timestamp, no way to know which document caused it."

03c · One more thing

Verification history: every attempt, one view

The more we talked to agents, the more a pattern came up. They couldn't tell what a user had tried before. Had they already attempted verification? Was there a previous attempt that got unlinked? Which one changed the name? They were always looking at a single snapshot with no backstory.

So we built a Verification History modal on the user profile. Every KYC, PAN, bank, and UPI attempt, in order, with status and timestamps. And you can click into any attempt to see the full detail right there.

Screen 3 — Verification history modal
The Verification History modal. KYC, PAN, Bank, and UPI each get their own tab. The left panel shows each attempt with its status (Verified or Unlinked) and timestamp. Click any attempt and the full detail loads on the right: Aadhaar image, OCR data, verification decision.
What the history view unlocked for agents
Full attempt timeline
Every attempt across KYC, PAN, Bank, and UPI, in one place, with exact timestamps.
Status per attempt
Each attempt clearly labelled as Verified or Unlinked, so agents can see at a glance what changed and when.
Drill into any attempt
Click any attempt and the full detail loads: image, OCR fields, API response. No new page, no extra navigation.
Why a modal and not a separate page

Agents are usually mid-conversation when they need to look something up. Sending them to a separate page and back would have broken that flow completely. The modal keeps them on the user profile. The tab structure (KYC, PAN, Bank, UPI) matched how agents already thought about verification types, so there was nothing new to learn.

05 · Impact

What changed for agents and users

Eliminated
Backend escalation for standard KYC issue types. Agents resolve end-to-end within the CS panel.
Faster
Resolution times. No re-submission of documents. No waiting on backend tickets.
Closed
Critical name change audit gap. A compliance record now exists where none did before.
06 · What I learned

What stayed with me

01
Tooling debt is quiet until it isn't
KYC got skipped because the product was moving fast. By the time it became a problem, the manual load was enormous. Internal tools are easy to deprioritise. They're also the ones that slow everything down when they don't exist.
02
Saying no to a feature is also design
The verification log page sounded useful. But once we understood that OCR and Digilocker queries never reach the manual queue, it became obvious the log would always be empty. Descoping it wasn't laziness. It was the right call.
03
The edge cases are where it gets interesting
The name change trail wasn't on anyone's list. We found it by asking what happens when the wrong Aadhaar gets verified. Once we pulled that thread, the compliance risk was obvious. The most important design decisions in this project came from scenarios nobody thought to raise.
