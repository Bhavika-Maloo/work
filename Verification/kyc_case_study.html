KYC Verification Tool for CS agents

CS agents had no way to look up a user's Aadhaar status. Every single query went to the backend team. This is how we fixed that.

Role
Product Designer
Domain
Fantasy Sports Platform
Surface
Internal CS Tool (MSD)
Type
0 to 1 feature build
01 · The problem

8,000+ tickets a month. All manual.

PAN and bank verification had CS panels. Aadhaar had nothing. Every query meant agents asking users to re-share details over chat, raising a backend ticket, and waiting up to 24 hours across three teams. No visibility. No self-serve. Just a broken loop running at scale.

8–15k

12–24h

3 teams
Required to resolve a single query end-to-end

"I'd ask the user for their details, raise a ticket, and then just wait. Sometimes it would come back in a day. Sometimes longer. I had no way to check anything myself."

What agents actually said

"The name changed on the account and now neither I nor the user knows what happened."

The finding that changed scope

Silent name changes after Aadhaar verification. Zero traceability. Not in anyone's brief.

03 · Solution

A KYC section inside the MSD panel

Modelled on the existing PAN Verification page so agents had zero learning curve. One place to see everything and act on it.

Screen 1 — KYC verification queue
Pending cases with PAN vs KYC name match %. Filterable by status, reassignable across the team.
Screen 2 — KYC document detail view
Aadhaar image alongside OCR-extracted fields. KYC API result, verification decision, and raw API response below.
Design decisions
Raw API data hidden by default

Structured fields first. Raw response collapsed below for edge-case debugging only.

OCR and image grouped together

Agents compare document image against extracted data in one glance. Separation means scrolling mid-investigation.

No direct KYC editing

View and unlink only. Any change goes through maker-checker to prevent accidental modifications.

Backend gap fixed before design finalised

System only surfaced verified states. Flagged pending and rejected as missing. Fixed before handoff.

Full KYC visibility
Doc type, number, name, DoB, GPS state, and status for every user.
Status with rejection reason
Verified, pending, rejected — all shown. Rejected cases surface the reason inline.
OCR and Digilocker detail
Uploaded image, IDFY validation, OCR response, and Digilocker data in one panel.
KYC unlink (maker-checker)
Agents can unlink for wrong Aadhaar, restricted state, or multi-account conflicts.
03b · The insight we caught

The name change nobody was tracking

Not in any brief. Every Aadhaar verification silently overwrites the account name. Wrong doc verified? Identity changed, original gone, zero traceability. Compliance risk nobody had thought to address.

"Once the name changed, it was just gone. No record of the original, no timestamp, no way to know which document caused it."

03c · One more thing

Verification history: every attempt, one view

Agents were always looking at a snapshot. No way to know if a user had tried before, which attempt got unlinked, or which one changed the name. We built a Verification History modal — every KYC, PAN, bank, and UPI attempt in order, with status and timestamps. Click any attempt for full detail.

Screen 3 — Verification history modal
KYC, PAN, Bank, and UPI tabs. Each attempt shows status and timestamp. Click any to load full detail on the right.
Modal, not a separate page

Agents investigate mid-conversation. A separate page breaks context. Modal keeps them anchored to the user profile.

Tabs match agent mental model

Agents already think in KYC, PAN, Bank buckets. Zero learning curve. A flat list would be slower to scan.

What actually changed

06 · What I learned

What stayed with me

01
Tooling debt is quiet until it isn't
KYC got skipped when the product was moving fast. By the time it surfaced, the manual load was enormous. Internal tools are easy to deprioritise and expensive to ignore.
02
Saying no to a feature is also design
OCR and Digilocker queries never hit the manual queue. The standalone log page would always be empty. Descoping it wasn't laziness.
03
The edge cases are where it gets interesting
The name change trail came from pulling one thread. The most important decisions here came from scenarios nobody thought to raise.
