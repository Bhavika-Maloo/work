The Business Problem

A new regulation was about to force 26% of users — generating 64% of revenue — through our most broken funnel.

Dream11 operates in a regulated industry. When MEITY signaled mandatory Min-KYC verification before deposits, we ran the numbers on who'd be affected. The answer was the cohort that paid for the company.

The User Problem

The system worked. Just not for users.

When we mapped what users actually hit, three symptoms kept showing up. They looked unrelated. They had the same root cause.

Old verification on deposit (Play Store). Triggered before commitment. Five document options on a single screen. Reads as a customs form, not a product flow.

End-to-end pre-revamp flow — drop-off concentrated at the verification step.

  • Symptom 01 — Withdrawal walls

    Users reached withdrawal and discovered their PAN, KYC, and bank account names had to match. By then, the mismatch was already baked in. Nothing at deposit had warned them.

  • Symptom 02 — PAN entry failures

    88% of PAN verification failures were data-entry mismatches. Users were re-typing names the system already had on file from prior KYC.

  • Symptom 03 — Re-verification fatigue

    Already-verified users were being asked to verify again to satisfy the upcoming regulation. Each touchpoint behaved as if prior verification didn't exist.

The root cause

Verification was built as a sequence of independent forms, each unaware of the others. Three symptoms, one structural problem.

Three users in three different verification states. The system treated them all the same.

Re-verification path

One layer that shaped every decision: the majority of Dream11's user base lives in tier 2 and tier 3 India — only 28% are from tier 1 cities. For this audience, sharing personal documents online isn't routine. Asking for Aadhaar at the wrong moment doesn't just create friction — it triggers active distrust. The same flow that works in Bangalore can fail in Jaunpur.

What the data ruled out

The fix wasn't a better verification screen, a better OCR engine, or better explainer copy. The fix was a system that knew what it already had — and asked the right user for the right document at the right time.

The Insight

The fix wasn't a better form. It was a connected system.

Design Principle

Verification only works when every touchpoint knows about every other touchpoint.

The old system was four independent forms — deposit, withdrawal, PAN, bank — none of which shared what they knew. The new system makes each touchpoint aware of the others: warn ahead, fill in behind, never ask twice.

The Solution · Deposit, End-to-End

Move the ask. Sequence the steps. Set expectations for what comes after.

Deposit is the simpler of the two flows. The win was timing — verification triggers after commitment, not before — and sequencing, where each screen prepares the user for the next.

First fix · Timing

KYC moved from before contest selection to after team creation.

In the old flow, KYC interrupted users before they had built a team or joined a contest. Zero sunk cost. Walking away cost them nothing. We moved verification to post-team-creation, pre-payment. By then, users have spent 3-5 minutes selecting players, picking a captain, building their squad. Now walking away costs them.

A/B test: +30% lift in Registration → Cash Add Page funnel for the test group versus control. Honest framing of this number is in the Outcomes section.

The new deposit flow, screen by screen

Same destination as the old flow — but each screen has a single purpose, and the verification step now sets expectations for withdrawal-time requirements before commitment.

Four-step deposit flow: contest commitment → expectation setting → location → document verification.

Sequenced, not stacked

The old flow asked everything at once on a single screen. The new flow breaks it into four single-purpose steps with clear progress: contest selection, what to expect, location, document.

Withdrawal warning at deposit

The line "You can withdraw Winnings only if your Govt ID & Bank name match" appears at the document selection step — before the user commits — so withdrawal-time mismatches stop being a surprise.

Second fix · Form intelligence

PAN entry knows what KYC already collected. Stop asking for data we have.

88% of PAN failures were data-entry mismatches — users typing names, DOBs, and numbers the system already had on file. The form was actively producing failure. Four UI changes, each tied directly to a failure category in the data:

  • Pre-fill name from KYC at PAN entry — eliminates the 40% name-mismatch class.
  • Calendar picker for DOB instead of free-text — eliminates the 21% DOB mismatch class.
  • Inline PAN format validation — catches invalid PAN at entry, not after submit.
  • Field-appropriate keypads — alphabetic for name, numeric for PAN, calendar for DOB.
Third fix · Error recovery

Every error becomes a route. Failure is never a dead-end.

When verification failed, the old system told the user it failed and stopped. No alternative path, no fallback, no escape. The new system uses one error component for every failure type — Aadhaar not linked, record already in use, OTP timeout, technical fault. Each shows a specific reason and a one-tap switch to a different verification method. Switching is easier than retrying.

Four causes, one component. Every error offers a way out — never a wall.

The Solution · Withdrawal, End-to-End

A conditional state machine. Same components, three paths.

Withdrawal is harder than deposit because users arrive in three different verification states. The flow has to detect which state they're in and route them through the right path — without making any of them feel like a special case.

Same entry for all users. The flow branches behind the scenes based on what's already verified.

Branch A · No KYC done

First-time withdrawer

User has played but never been put through KYC. Full path: Email → Verify Lite (Aadhaar) → PAN. Three steps, three progress bars.

Branch B · Aadhaar Lite/OCR

Returning, partially verified

System detects prior Lite verification. Re-verification screen reframed as "Re-verify with your Aadhaar as a final check" — acknowledges the prior step instead of pretending it didn't happen.

Branch C · RE-KYC required

Cleanup cohort

Existing users whose verification didn't meet the new standard. Routed through a dedicated re-KYC path with the same "final check" framing — minimizes churn risk on the high-value cohort.

Fourth fix · Copy as routing

For users who already verified once: "as a final check" — not "verify again."

User Type C — already Aadhaar Lite/OCR verified — would need to re-verify under the upgraded standard. Asking them to verify again risked a "we don't trust you" perception and high churn. We reframed re-verification as completion, not repetition. The screen acknowledges prior verification and presents the new step as the last one in a sequence. Same data collected. Different psychology.

The full state machine

Users don't see the branching. From their perspective, they tap "Verify to Withdraw" and land on the right path. The complexity is absorbed by the system, not surfaced to the user.

The full conditional flow: one entry, three paths, converging on PAN entry and final withdrawal.

Bank verification handles its own state machine: success, name mismatch with PAN, manual proof upload as fallback. Every failure mode has a defined recovery path.

One entry, three paths

The branching logic is invisible to users. They tap "Verify to Withdraw" and land where the system thinks they should be. The complexity is absorbed by the architecture.

The "Maybe Later" trade-off

For users where PAN was optional at this step, we allowed deferral via a "Maybe Later" CTA. This protected the funnel but introduced a known risk: revenue-relevant data collection could be delayed indefinitely. Flagged in Outcomes.

On the funnel result, honestly

The 30% lift in Registration → Cash Add Page didn't fully propagate to Paid Contest Join. The downstream funnel was held flat. We absorbed compliance overhead without a conversion penalty — which, for regulatory work, is the realistic ceiling. Most teams shipping a forced KYC flow tank downstream conversion. We didn't.

Roads Not Taken

Four ideas that shaped the solution by not making it.

Good design choices are often the result of killing better-sounding ideas for non-obvious reasons.

qr_code_scanner
Dropped

Aadhaar QR Scan

Scan the QR, auto-fill the fields. Zero typing, zero uploads. But the Secure QR format with full demographic data only became standard from 2019, and a significant share of our user base had older cards that wouldn't work. Coverage gap was too large to ship on.

Killed by Coverage gap
link
Dropped

Aadhaar + PAN, no OTP

Since PAN-Aadhaar linkage is government-mandated, two numbers the user already knows could uniquely verify identity — no document upload, no OTP dependency. Clean and low friction. But it couldn't derive a user photo, failing the full KYC requirement.

Killed by No photo derivation
document_scanner
Dropped

OCR with inline correction

Instead of OCR failing silently, surface what it read and let users fix it upfront — the way Zomato handles address parsing. The concept was sound. The reality wasn't: Voter IDs and Driving Licences have different layouts in every Indian state. Too many variants, too little time.

Killed by India's document layout chaos
id_card
Dropped

Interactive Document Card UI

What if instead of a flat form, users tapped fields directly on a visual representation of their ID — spatial, intuitive, document-native? The idea was strong. But rendering a consistent card UI across every document type, on three platform variants, was technically infeasible within the timeline.

Killed by Tech complexity + timeline
Navigating Uncertainty

The rules changed three times while we were building.

A regulated-industry redesign isn't a linear project. We kept what was reusable, scrapped what was state-specific, and rebuilt the deposit gate from scratch.

stream Initial scope

Withdrawals only

We started with the withdrawal flow — verifying users at the point money exited the platform. Deposits would come later.

gavel Mid-flight pivot

Tamil Nadu RMG ban

State law changed mid-project. Tamil Nadu banned real-money gaming. Two flows we'd already designed for that state had to be scrapped entirely.

account_balance_wallet Final scope

Deposit + withdrawal

Final scope expanded: KYC gating both ends of the funnel. Bigger than what we signed up for. The component-based architecture meant we absorbed the change without starting over.

A regulated, multi-platform, conversion-critical funnel — redesigned in four months without breaking what was already working. The system now warns ahead, fills in behind, and never asks twice.
