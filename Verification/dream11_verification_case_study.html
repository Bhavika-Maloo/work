§ 01 — Business Problem

The 26% / 64% problem.

A regulation was about to force our highest-revenue cohort through our most broken funnel.

Context

Three forces converged at the same time:

  • Regulatory ambiguity. MEITY (Ministry of Electronics and Information Technology) was expected to mandate Min-KYC verification before deposits. Timeline was unconfirmed; rules could land any day.
  • Platform fragmentation. Verification logic differed across iOS, APK, and Play Store. Play Store enforced state and age via Aadhaar Lite; APK and iOS relied on self-declaration. Same product, three rule-sets.
  • Funnel cost of compliance. KYC was the largest single drop-off in the registration-to-deposit funnel. Adding more mandatory verification would deepen the leak — unless the design absorbed it.

The constraint we set: add mandatory verification ahead of the regulation, without breaking the funnel that paid for the company.

§ 02 — User Problem

Three symptoms, one root cause.

Users weren't dropping off because verification was hard. They were dropping off because the system pretended each step was independent.

Visual 2.1 End-to-end flow with drop-off annotations
[ Wide horizontal "Current Flow" image ]

Reg → Contest Selection → Create Team → Verification (55% drop) → Payment (10% drop) → UPI PIN (30% drop)
End-to-end pre-revamp flow. The 55% drop at the verification step was the largest single leak in the journey from registration to first deposit.
Symptoms

We mapped three symptoms that all looked unrelated:

  • Withdrawal walls. Users reached withdrawal and discovered their PAN name, KYC name, and bank account name had to match. By then, the mismatch was already baked in. Nothing at deposit had warned them.
  • PAN entry failures. 88% of PAN verification failures were data-entry mismatches. Users were re-typing names that the system already had on file from earlier KYC.
  • Re-verification fatigue. Already-verified users were being asked to verify again to satisfy the upcoming regulation. They felt harassed. Each touchpoint behaved as if prior verification didn't exist.

The root cause: verification was built as a sequence of independent forms, each unaware of the others.

§ 03 — Who We Were Solving For

Three user types, three entry states.

Each type entered the system in a different state. The redesigned flow had to route them differently — same components, different paths.

A
New user

No KYC done

Hit the Aadhaar OTP screen at deposit. Often dropped off when uncomfortable sharing Aadhaar — a finding from qualitative research.

B
Existing — high value

PAN-verified only

Verified for tax purposes but never put through Aadhaar or state checks. ~26% of users, ~64% of revenue. The MEITY-vulnerable cohort.

C
Existing — partial

Lite/OCR verified

Already Aadhaar-verified through a lighter method (Lite or OCR). Would need to re-verify under the upgraded standard.

§ 04 — How We Collected Data

The unanswered questions mattered as much as the answered ones.

Methods

Quantitative. Cohort distribution by PAN/Aadhaar status. PAN failure mode breakdown — which revealed that 88% of failures were UI-addressable, not technical. TAT and automation rates from the data team.

Qualitative. Moderated user research with the existing verification flow. One quote that shaped our approach: "AADHAR OTP misuse ho sakta hai (camera access karke)" — users feared misuse, not the data sharing itself.

Guerilla. N=19 in-person sessions on document priority. Result: Driving Licence preferred (most handy), then Voter ID, then PAN. Passport rarely usable.

Got the data
  • Cohort split by PAN × Aadhaar status
  • PAN failure mode breakdown (5 categories)
  • TAT for 90% of verifications (12 min)
  • Document priority by user availability
  • Qualitative reactions to mandatory verification
  • Existing automation rate for PAN flow
Couldn't get → designed defensively
  • % retry vs. % switch on error → made switching the easier action
  • Verification step completion at cohort level → flagged for v2 instrumentation
  • "Maybe Later" PAN return rate → noted as open metric
  • Churn by error type → designed all errors to recover gracefully
  • Average attempts to complete KYC overall → only had it for PAN

§ 05 — The Principle

The design spine.

Principle

Verification only works when every touchpoint knows about every other touchpoint.

The old system asked users to remember things across steps that took weeks to traverse. The new system makes the system itself remember — and warn ahead, fill in behind.

§ 06 — Problem → Solution

Four design moves.

One per symptom. Each tied directly to a problem. Each derived from research or data.

Move 01

Deposit aware of withdrawal.

Problem
Users mismatched names at withdrawal because nothing at deposit told them it would matter.
Fix
Surface withdrawal requirements at deposit time. Mirror the warning at withdrawal so the message reinforces, not surprises.

Move 02

PAN aware of KYC.

Problem
88% of PAN failures were data-entry errors. Users were typing names the system already had on file.
Visual 6.3 PAN failure mode breakdown
[ Bar chart ]

Name mismatch 40.08% · DOB mismatch 21.25% · Invalid PAN 15.19% · Name & DOB 11.87% · KYC details 10.36% · Technical 1.03%
Diagnostic breakdown. Almost no failures were technical. The fix had to be in UI, not in the API.
Fix
Four UI changes derived directly from the failure modes:
  • Pre-fill name from KYC at PAN entry — eliminates the 40% name-mismatch class entirely.
  • Calendar picker for DOB instead of free-text — eliminates the 21% DOB mismatch class.
  • Inline PAN format validation — catches invalid PAN at entry, not after submit.
  • Field-appropriate keypads — alphabetic for name, numeric for PAN, calendar for DOB. Removes the user's need to manually toggle.

Move 03

Errors as routing, not dead-ends.

Problem
Error states in the old system were dead-ends. A failed Aadhaar OTP told the user it failed and stopped there.
Fix
Every error becomes a routing moment. One component pattern across all error types: clear reason, alternative paths, escape to help.
Visual 6.5 Error states — system pattern
[ Error state grid ]

Aadhaar not linked · Record already in use · Something went wrong · OTP failure
(highlight consistent component structure)
Four causes, one component. Every error offers two things: a specific reason and a one-tap switch to a different verification mode. We didn't have data on retry-vs-switch behavior, so we made switching the easier action by default.
Move 04

Re-verification as completion, not repetition.

Problem
Already-verified users (Aadhaar Lite / OCR) had to re-verify under the new standard. Risk of churn from a "we don't trust you" perception.
Fix
Frame re-verification as completion, not repetition. A copy decision tied to the research finding that prior effort needed to be acknowledged.
Visual 6.6 Re-verification screen — old vs. new copy
[ Side by side ]

LEFT: "Verify your Aadhaar"
RIGHT: "Re-verify with your Aadhaar as a final check"
Reframing the same step as the last step rather than another step changed how it felt. Small fix, specific job: protect the existing-user cohort during a forced re-verification cycle.
§ 07 — Outcomes

Shipped. Measured. Open.

An honest split. Not everything moved. Not everything was measurable. The Open column is real.

Shipped
  • Unified verification across iOS, APK, Play Store
  • Conditional routing engine — same components, different paths by user state
  • Reason-specific error states with one-tap mode switching
  • Deposit ↔ withdrawal awareness via cross-step warnings
  • Re-verification flow with "final check" framing
  • Architecture portable to deposit-side verification when MEITY mandates land
Measured
  • PAN success rate: ~50% → ~72%
  • PAN TAT: 12 min → 2–4 sec
  • PAN automation: ~90% → 99.99%
  • Avg. attempts to complete PAN: 2
  • Reg → Cash Add Page funnel: +30% (TG vs. CG, A/B tested)
  • 7-day R→D & Paid Contest Join: held flat
Open
  • Verification-step completion rate at cohort level — flagged for v2 instrumentation
  • Bank verification 48-hour lock state — descoped, needs v2 redesign
  • "Maybe Later" PAN deferral — return rate not measured; risk of indefinite revenue-data delay
On the funnel result, honestly The 30% lift in Registration → Cash Add Page didn't fully propagate to Paid Contest Join. The downstream funnel was held flat. We absorbed compliance overhead without a conversion penalty — which, for regulatory work, is the realistic ceiling. Most teams shipping a forced KYC flow tank downstream conversion. We didn't.
§ 08 — Roads Not Taken

Four ideas that shaped the solution by not making it.

Good design choices are often the result of killing better-sounding ideas for non-obvious reasons.

Dropped

Aadhaar QR Scan

Scan the QR, auto-fill the fields. Zero typing, zero uploads. But the Secure QR format with full demographic data only arrived in 2019, and a significant portion of our user base had older cards that wouldn't work.

Killed by Coverage gap
Dropped

Aadhaar + PAN, no OTP

Since PAN-Aadhaar linkage is government-mandated, two numbers the user already knows could uniquely verify identity: no document upload, no OTP dependency. Clean and low friction. But it couldn't derive a user photo, failing the full KYC requirement.

Killed by No photo derivation
Dropped

OCR with inline correction

Instead of OCR failing silently, surface what it read and let users fix it upfront — like Zomato does with address parsing. The concept was sound. The reality wasn't: Voter IDs and Driving Licences have completely different layouts across every Indian state. Too many variants, too little time.

Killed by India's document layout chaos
Dropped

Interactive Document Card UI

What if instead of a flat form, users tapped fields directly on a visual representation of their ID — spatial, intuitive, document-native? The idea was strong. But rendering a consistent card UI across every document type, on three platform variants (iOS, APK, Play Store), made it technically infeasible within the timeline.

Killed by Tech complexity + timeline
§ 09 — Reflection

What I'd do differently.

Three angles. Pick the one most true to what you'd actually change. Don't write a generic reflection.

Option 1 I'd start with error-state mapping before happy-path design. Most of the system insight came from staring at failure modes, and I arrived there late.
Option 2 I'd commit to instrumenting the verification-step completion rate from day one. The metric I care most about is the one I can't fully claim post-hoc.
Option 3 I'd push harder on the bank verification 48-hour lock state. Shipping it as-is created a hostile UX moment that v2 still has to fix.
